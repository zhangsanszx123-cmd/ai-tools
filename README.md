# AI 工具导航

## 本地运行

1. 安装依赖：`pnpm install`。
2. 参考 [.env.example](./.env.example) 配置环境变量。数据库可继续放在已有 `.env` 中，`.env.local` 仅填写需要覆盖或新增的配置，不要用空值覆盖现有数据库连接。配置 `DATABASE_URL` 和 `DB_CA_CERT`；CA 支持 PEM、包含 `\n` 的 PEM 或证书文件路径。所有数据库连接始终校验 SSL 证书，不要将凭据提交到版本控制或发到聊天中。
3. 新数据库先按下文初始化认证表，再审阅并执行 [db/directory-v2.sql](./db/directory-v2.sql)，创建分类、正式工具、投稿记录三张业务表，并初始化 17 个分类。现有项目数据库已经完成此步骤，不要重复建表。旧版单表脚本 [db/schema.sql](./db/schema.sql) 已停用；旧结构迁移需参考 [设计文档](./docs/database-design.md)，不可覆盖旧数据。
4. 执行 `pnpm dev`。修改环境配置后需重启开发服务。

首页分类从 `ai_directory_categories` 动态读取，不再依赖代码内置数组。仅展示启用分类下 `ai_directory_tools.status = 'published'` 的工具。没有工具时显示真实空目录，不填充演示数据。`featured_order` 非空的工具进入热门列表，按数值升序排列；`published_at` 用于最新收录；同分类按 `display_order`、收录时间排序。

## 登录与投稿

登录注册参考 [Next.js with-supabase 示例](https://github.com/vercel/next.js/tree/canary/examples/with-supabase) 的表单、密码确认、Cookie 会话与页面保护流程，后端使用 Better Auth + 当前 PostgreSQL，不需要 Supabase 或 Neon Auth 服务。

1. 配置 `BETTER_AUTH_SECRET`（至少 32 字符的高熵随机值）和 `BETTER_AUTH_URL`（本地 `http://localhost:3000`；部署后填写实际 HTTPS 域名）。密钥示例生成方式见 [.env.example](./.env.example)，不要每次启动重新生成。
2. 使用 Node.js 22.18+ 或 24，执行 `pnpm auth:check` 只读检查认证表；确认后执行 `pnpm auth:migrate` 创建缺失的认证表和索引。当前账号若没有 `public` 建表权限，但有数据库 CREATE 权限，迁移会创建账号同名的自有 schema，利用默认 `"$user", public` 搜索路径隔离认证表，不改变 `public` 权限。也可审阅并手动运行 [db/auth-schema.sql](./db/auth-schema.sql)。迁移命令拒绝修改已有表的列，不会操作目录表或 Neon Auth 表；应用启动不会自动建表。
3. 访问 `/login` 登录，或 `/login?mode=signup` 注册。注册只需填写邮箱、密码与确认密码，密码为 8–128 字符，昵称自动设为“新用户”。注册成功自动登录，默认进入个人中心；从投稿入口进入时会返回投稿表单。

密码由 Better Auth 使用 scrypt 加盐哈希，不存储明文。会话有效期 7 天，使用 HttpOnly、SameSite=Lax Cookie，HTTPS 生产环境自动加 Secure。退出会撤销数据库会话；受保护页面与服务端操作都验证会话。认证 API 使用数据库持久化限流：每 IP 每分钟最多登录 10 次、注册 5 次。部署时请确保反向代理覆盖客户端传入的地址头。

前台用户只属于 `ai_directory_users`。后台使用独立的 `admin_user`，不读取前台 `role` 获取管理权限，不复制前台用户或密码。即使前台旧账号的 `role` 为 `admin`，也不能登录后台。现有 Neon Auth 用户不会被自动导入或更改。未接入邮件发送，因此不展示邮件验证或找回密码入口。

## 独立后台认证

- 后台登录 `/admin/login`；认证 API `/api/admin-auth/*`；前台仍使用 `/login` 和 `/api/auth/*`。
- 后台独立使用 `admin_user`、`admin_account`、`admin_session`、`admin_verification`、`admin_rate_limit` 五张表，Cookie 前缀 `ai-tools-admin`，会话有效期 8 小时；前台 Cookie 前缀仍为 `ai-directory`，会话有效期 7 天。双方互不识别、互不覆盖，退出一侧不撤销另一侧会话。同一个邮箱可分别存在于两套账号中，密码独立。
- 后台 API 仅开放登录、退出和会话读取，不开放注册、资料修改或找回密码。登录每 IP 每分钟最多 5 次；停用 `admin_user."isEnabled"` 后既有会话也无法访问管理页面和操作。
- 当前数据库已创建后台认证表。新数据库初始化三张业务表后，先执行 `pnpm admin:check`，确认后执行 `pnpm admin:migrate`。对应 SQL 为 [后台认证表](./db/admin-auth.sql) 和 [独立管理员关联迁移](./db/admin-audit-migration.sql)。只新增表、列、索引，不转换前台账号。
- 首个管理员由数据库维护者在本机执行 `pnpm admin:create` 创建，交互输入邮箱及密码（12–128 字符，隐藏输入并要求确认）。不要把密码放在命令行、Git 或聊天中；密码使用 Better Auth scrypt 哈希。系统没有默认管理员或默认密码。
- 新审核和发布记录写入 `reviewed_by_admin`、`created_by_admin`，关联 `admin_user`；旧 `reviewed_by`、`created_by` 仅保留历史，不修改或伪造原审核人。

## 投稿、审核和管理员使用

- 普通用户在个人中心“提交工具”填写工具信息，图片会解码并转为 WebP。投稿仅进入 `ai_directory_tool_submissions`，不会提前公开。
- “提交历史”可分页查看原始内容、私有图片、审核状态和驳回原因。驳回后可重新投稿，旧记录保留。
- 管理功能位于独立后台 `/admin`，后台登录入口为 `/admin/login`。仅前台登录时访问 `/admin/` 仍会显示后台登录页，不会读取前台身份。首页右上角和页脚提供“后台管理”入口。
- 后台侧栏包含“审核队列”（`/admin?tab=review`）、“分类管理”（`/admin?tab=categories`）、“AI 工具”（`/admin?tab=tools`），支持退出登录和返回前台。个人中心仅保留投稿、历史和个人信息；旧管理链接会跳转到新后台。
- 通过审核时，单条数据库事务新增正式工具并关联原投稿；驳回必须填写原因。并发审核不会重复发布，Slug 冲突完整回滚。页面与所有管理操作均在服务器校验管理员权限。
- 分类管理支持新增、名称/短名/说明/图标/排序修改和启停，分类标识创建后固定。停用会隐藏该分类下所有公开工具，并禁止新投稿和通过审核；不删除已有内容。
- 分类管理默认是表格列表，展示名称/标识、短名、图标、排序、状态与操作；支持关键词、启停状态筛选及分页，新增和编辑使用独立表单。行内停用需要确认隐藏关联工具，启用后恢复展示；行内状态更新不覆盖其他字段，过期状态提交会被拒绝。
- 分类管理与 AI 工具共用完整分页栏，即使只有一页或零条记录也显示。默认每页 10 条，可选 20/50/100 条，提供首页、上一页、页码、下一页、末页及跳页；切换条数回到第一页，翻页和跳页保留关键词、状态与分类筛选。超出范围的页码自动落到有效页，空列表显示第 1/1 页。AI 工具使用数据库 LIMIT/OFFSET 分页。
- 工具管理支持直接收录、修改正文/分类/图片、热门排序、分类内排序和上下架。已收录 Slug 固定；不上传新图时保留旧图，勾选移除时清除，上传新图优先替换。原投稿快照不随正式工具编辑改变。
- 工具管理默认是表格列表，支持按名称/标识/网址关键词、分类、上下架状态组合查询，分页保留筛选条件。点击“新增工具”或行内“编辑”进入独立表单；行内可直接上下架。
- 行内“删除”展开确认区，必须勾选确认后提交。删除写入 `deleted_at` 并下架，不物理删除工具，保留投稿快照、审核关联与 Slug 唯一性；从公开目录、详情、公开媒体及普通管理列表中排除。旧编辑页不能重新保存或上架已删除工具。目前不提供自助恢复入口，维护者可在核实后通过数据库恢复。现有库使用 [工具管理增量 SQL](./db/tool-management.sql)，`pnpm admin:migrate` 会包含此增量。
- 公开媒体接口是 `/api/tool-media/[slug]/[kind]`；私有投稿媒体接口是 `/api/submission-media/[id]/[kind]`。私有资源只允许投稿本人或管理员访问，均不缓存；公开资源也每次检查分类启用和工具发布状态。
- 后台新增“前端用户”（`/admin?tab=users`）和“后端用户”（`/admin?tab=admins`），支持按名称/邮箱搜索、状态筛选、完整分页、新增与编辑账号、重置密码、启停和确认删除。首个管理员仍通过本机 `pnpm admin:create` 创建；后续管理员可由已登录管理员在后台维护。所有后台管理员拥有完整管理权限，不通过前台 `role` 授予后台权限。
- 前台密码要求 8–128 字符，后台密码要求 12–128 字符；编辑时留空保留原密码。重置密码或停用账号会撤销该账号旧会话，管理员重置自己密码后需重新登录。当前管理员不能停用或删除自己，服务端同样校验。删除账号会清除凭据和会话，保留投稿、正式工具与审核记录，原身份关联置空；删除需勾选确认，不提供恢复入口。
- 应用不会在启动时自动建表、迁移或插入工具数据。首页空工具列表是正常状态，管理员收录或通过投稿后才展示。

## 本地图片与独立图片服务器

图片存放于持久磁盘，数据库的 `logo_url`、`cover_url` 保存相对 URL。默认目录为项目的 `storage/media/`，可通过 `MEDIA_STORAGE_DIR` 指定服务器持久目录。`public/` 子目录存正式工具图片，`private/` 子目录存私有投稿图片；不要把整个存储根目录配置成公开静态目录。文件统一为 WebP，以内容 SHA-256 命名，重复图片复用文件。

后台“图片存储设置”（`/admin?tab=media`）默认填写 `/`，由当前网站的 `/media/<hash>.webp` 读取本地文件；该接口检查工具发布状态与分类启用状态。填写完整 HTTP/HTTPS IP、域名或路径前缀后，正式工具的公开图片地址统一拼接该前缀。配置支持测试图片访问、保存和恢复默认；HTTPS 网站必须使用 HTTPS 图片服务器。修改地址不会修改每条工具记录。

切换独立服务器前，需把 `storage/media/public/` 中的文件同步到对方的 `/media/` 访问路径。地址设置只切换读取位置，不自动搬运图片，也不通过 HTTP 上传新文件；新上传仍写本机持久目录，独立服务器需要同步这些文件。外部静态服务器直链的访问策略由该服务器控制，下架不会自动删除远程文件。私有投稿图片始终使用当前网站的权限接口，不拼接公开服务器地址；审核通过时生成独立的公开文件引用，原私有图片保留。

已有数据库由维护者执行 `pnpm media:migrate --prepare`：添加 [URL 字段和配置表](./db/media-storage.sql)，分批导出所有图片，逐文件校验 SHA-256，并回填相对 URL，暂保留旧二进制。完成应用升级并验证后执行 `pnpm media:migrate --finalize`，再次校验后清空旧二进制和 MIME 字段，并新增禁止写回二进制的约束。两个阶段均支持重试，数据库修改在单个事务中完成，失败回滚；校验过的磁盘文件保留以供重试。`pnpm admin:migrate` 包含 URL 结构增量，但不会自动导出或清空图片。

存储目录不纳入 Git 或构建产物，部署时应使用持久卷或独立持久路径；备份和恢复必须同时包括数据库与图片目录。一次性图文补齐脚本已使用相同的本地文件和相对 URL 写入方式，不再写入二进制字段。新部署初始化认证、目录及后台表后，同样需要执行 `pnpm admin:migrate` 准备图片 URL 结构。验证文件与地址处理可执行 `pnpm test:media`。

## 检查与测试

| 命令 | 用途 | 数据影响 |
| --- | --- | --- |
| `pnpm directory:check` | 检查三表必要字段、SSL 和记录数量 | 只读 |
| `pnpm test:auth` | 认证生命周期、哈希、跨站防护、限流 | 内存数据库 |
| `pnpm test:directory` | 内容、分类、排序、URL 与 ID 校验 | 无数据库写入 |
| `pnpm test:directory-db` | 三表业务、权限、并发审核、冲突回滚、快照与分页 | 随机 `dir_test_*` 隔离 schema，测试后删除 |
| `pnpm build` | 生产构建与类型检查 | 仅本地构建产物 |
| `pnpm test:directory-e2e` | 构建后启动随机端口生产服务，测试真实表单和接口 | 随机 `dir_e2e_*` 隔离 schema，测试后删除 |
| `pnpm test:auth-pages` | 检查正在运行的应用页面与未登录跳转 | 只读 HTTP |

数据库集成测试需要当前数据库角色具备创建自有 schema 的权限。测试只在本次随机创建的 schema 中生成临时账号/内容并清理，不修改实际用户、角色或业务记录。端到端测试前先执行 `pnpm build`。`pnpm exec tsc --noEmit` 可单独检查类型。

部署时将 `BETTER_AUTH_URL` 设置为实际 HTTPS 域名，配置 `DATABASE_URL`、`DB_CA_CERT` 和稳定的 `BETTER_AUTH_SECRET`。本地生产预览不加载 Vercel 专用分析脚本；只有 Vercel 环境才启用该集成。

## 排查目录无法加载

- 开发页面提示数据库未配置：检查 `.env.local` 中的 `DATABASE_URL` 是否为空，并重启服务。
- 服务端日志代码 `42P01`：目录表不存在，执行建表脚本。
- 代码 `42703`：已有表缺少应用所需字段，核对数据库结构。
- 代码 `28P01`：检查连接账号与密码。
- 代码 `ECONNREFUSED`、`ENOTFOUND` 或连接超时：检查主机、端口、网络和数据库状态。

连接失败时页面保留不可用提示；不会将失败伪装成空目录或演示数据。服务端只记录错误代码，避免泄露 SQL、连接字符串和用户数据。
